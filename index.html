help
table name decides what the three database tables are called — iw_par_<name>_param, iw_par_<name>_groups and iw_set_<name>. Lowercase letters and digits, e.g. kjol. plant number is used only in the SQL file's name; it is not written into the database.

Below, the badge after each option is its default; hovering a checkbox shows the same summary.

Addressing

  • subtract_oneon — type addresses exactly as the device documentation prints them; this one switch converts them all. Leave it on when the documentation counts from 1, which most do — including 4xxxx lists, where 40101 is entered as 101 and polled as 100. Turn it off only when the documentation already gives zero-based protocol addresses. If any address would end up below 0, validation stops you.

Script shape

  • truncateon — empty the table first with TRUNCATE TABLE, which is what you want when re-importing.
  • create_tablesoff — add CREATE TABLE IF NOT EXISTS. Needed the first time a plant gets this table.
  • Neither does anything in the default format. modern always creates the table and uses REPLACE INTO rather than empty-then-insert, so these two only matter with sql_format: legacy.

Alias text

  • use_system_noon · use_tagon · use_extraon — which of a point's fields go into the alias the operator reads. The order is fixed: system_no-tag-text-(extra) → 360.001-RT401-Romtemperatur-(1=Drift). A field left empty on the point adds nothing either way, and the point's text is always included.
  • proper_case_stateson — capitalise each word of a state text: drift på → Drift På, the same as Excel's WorksheetFunction.Proper. Affects the JSON and the plain form alike. Turn it off to keep Norwegian casing exactly as typed.

State texts

  • use_jsonon — the master switch, as in the Excel tool (Prot!B54). Off, every state text is silenced at once: no format_extra JSON and no list in the alias. The state ids stay in the project, so turning it back on restores them.
  • statetext_only_rwoff — on, only writable points (rw/vrw) get the state-text JSON. Read-only points keep their state list in the project but ship an empty format_extra.
  • statetext_in_aliasoff — on, the flattened state list is also written into the point's extra, so it shows up in the alias: …-(0=Av, 1=På). Divergence: with this off, Excel cleared the extra text of matched rows; here your extra is left alone (docs/07 §7.3).

Points and groups

  • force_activeon — write every point active=1, whatever its own active field says. Rows whose text is Reserve. stay inactive anyway. Divergence: in Excel force_active beat the Reserve rule; here Reserve wins, so a spare row stays inactive (docs/08 item 11).
  • include_minmaxoff — on, carry the point's range min and range max into the param record. Off leaves both blank even when the point has values, as the rest of the fleet does: the scaling table already supplies the raw and engineering limits.
  • override_decimaloff — on, fill dec from the unit table. A unit that has a decimals entry (Pa, ppm, m3/h → 0) overwrites the row's own value, as the Excel helper did; a unit without one leaves it alone.
  • auto_groupsoff — on, a point with an empty group takes its datatype's default group. You then set a group only where you want something different.
  • alarms_to_almoff — on, every point carrying an alarm letter (A/B/C/N) moves into the alm group. Only runs when auto_groups is on too — ticking this by itself changes nothing.

Motherwords

A bit-addressed point needs its whole word polled once. Any row reading that same address without a bit counts — no row has to be called "Motherword".

  • auto_motherwordson — missing word rows are created for you: read-only, in the same group as the bit that needed one. Leave it on unless you write motherword rows yourself.
  • require_motherwordsoff — on, a missing motherword blocks generation instead of warning. Off, you get a warning naming the addresses and the script is still produced.
  • exclude_motherwords_from_groupson — keep synthesized motherwords out of the display groups, so the operator sees the named bits rather than the raw word. Turn it off only if the word itself should appear in the menu.

Groups

help
Groups decide how points are grouped in the IWMAC display. Left field = the short key you type in a point's group column (aio), right field = the name shown to the operator (Analoge inn/ut).

Defining them

  • Every group a point uses must exist here — validation stops otherwise, and its fix: button can create the missing ones for you, key as alias, rename after.
  • The five defaults (aio dio alm misc sch) are what nearly every existing plant list uses — one click adds them, and the keys autocomplete in the points table.
  • Display order in IWMAC = row order here. Saving from the GUI writes that order, replacing any order numbers an imported project carried.

How they bind to points

  • The key becomes the first part of the point's element_id (aio_0_3_100) — pick keys before generating, not after; renaming later changes every id in the group.
  • auto_groups in the Project card fills empty group cells from the datatype's default, and with alarms_to_alm moves lettered rows to alm.
  • A point with no grp ticked keeps its param/set rows but stays out of the operator menu; synthesized motherwords are excluded on their own while exclude_motherwords_from_groups is on.

State texts

help
A state list translates a register's numeric values into words in IWMAC — instead of the operator seeing 2, they see Avriming. Typical use: operating-mode and status registers whose documentation says something like "0 = Off, 1 = Run, 2 = Defrost".

Building a list

  • Make one list per distinct enumeration in the device documentation, with a free-choice id (1, 2, 3 …). Several points share one list — define the enumeration once.
  • One state per line: value box, word box — 0 = Av, 1 = Drift. Enter in a word box (or + state) adds the next line with the value counted on. Pasting a whole vendor list like 0=Av 1=Drift into any word box fills all the lines at once.
  • Keep the vendor's numbers exactly; translate only the words (Norwegian). Values must be 0 or higher — an enum with negative values cannot be a state list; leave that point without one and say so.

Using it on points

  • Type the list's id in a point's state column. A point with a state list usually needs no unit, scale or decimals.
  • On generate it becomes the IWMAC state JSON in the point's format_extra; the words are Proper-cased unless proper_case_states is off.

The switches that affect state texts

All in the Project card: use_json is the master gate — off means no state texts at all, whatever the rows say; statetext_only_rw limits the JSON to writable points; statetext_in_alias also writes the flattened list into the point's extra, overwriting what is typed there.

Modbus variables

help
A Modbus variable is a row of the datatype table — the same Modbus_Variables sheet the Excel tool lets you unhide and edit. It supplies the read and write function codes, the raw type and the word order, so a point's datatype can only name one that exists.

When to make one

  • Only when no shipped key fits. 135 come with the tool and cover nearly everything; the datatype dropdown lists them all.
  • A new variable is a new combination of parts already in service — clone the nearest key and change the one field that differs. The dialog offers no free text for that reason: the driver understands the parts, not the name (docs/15).
  • You cannot redefine a shipped key. Excel's VLOOKUP takes the first match, so a second row of the same name would never take effect — it would only make one name mean two things in two files.

Where it goes

  • Into this project's file, so it travels with the list and works in the browser. It is not available to your other projects until you promote it or copy it.
  • Export Excel writes it into the workbook, so the macro can resolve it. Nineteen rows fit; past that the export refuses rather than writing where the macro cannot see it.
  • Promote — local GUI only — appends it to data/tables/datatypes.csv for every project on this machine. It reaches other people through a commit, not through the project file.

Points

help
One row per Modbus point. Minimum per row: group, datatype, addr, text. Hover any column header for its meaning, or press the ⓘ beside it for the long form — what the column is, what it feeds in the generated SQL, and when to use it. Columns are described below in the order they appear.

Identity — group, datatype, addr, bit

  • group — must exist in the Groups card, or validation stops. It also builds the point's key: element_id = <group>_<driver_id> (aio_0_3_100) unless the project file overrides it.
  • datatype — the single most consequential column: it supplies the read and write function codes, raw type, byte/word swap, application class and parameter type. The "common" group covers nearly everything: A_Hold_I16_N analog holding register · A_Input_I16_N analog input register · I_Hold_U16_N plain integer/counter · Digital_X_N discrete input · Coil_X_N coil · Bit_Hold/Bit_Input one bit inside a word · …_I32/U32/F for 32-bit values. If the doc says the word order is reversed (LSW first — energy meters often do), use the _W or _R variants. The key has to exist in the datatype table. The dropdown only offers keys that do, but a loaded project, a converted workbook or an imported SQL script can carry a spelling nothing describes: those rows are marked red the moment the list loads, Validate rejects them and Export Excel refuses to write the workbook at all — its macro derives every generated column from that same table. Pick a real key — or, when the register genuinely needs a combination none of them describes, make one in the Modbus variables card above and the project will carry it.
  • addr — the register number exactly as the device documentation prints it (strip a 4xxxx/3xxxxx prefix: 40101 → 101). The subtract_one option handles the 1-based offset globally — never subtract yourself. Address and datatype together give driver_id = 0_<readfunc>_<addr>.
  • bit — 0–31 for one bit inside the word, or nibble syntax 5#4; the bit is appended to the driver id (0_3_100.4). Use a Bit_* datatype, and the motherword row is created for you on generate. Alarm bits: alarm letter A + group alm.

Alias — system no, tag, text, extra

These four join in a fixed order to make the text the operator reads: system_no-tag-text-(extra) → 360.001-RT401-Romtemperatur-(1=Drift). An empty field contributes nothing, and use_system_no/use_tag/use_extra in the Project card switch the parts off wholesale.

  • system no — the plant's system number for this point, 360.001. Usually the same for a whole block of rows.
  • tag — the short component tag, RT401.
  • text — short Norwegian description; the only alias part that is always included. Reserve. marks a spare row: it stays in the list but is written inactive even with force_active on.
  • extra — the parenthesised suffix. Overwritten on generate when statetext_in_alias is on and the row has a state list.

Presentation — unit, scale, dec

  • unit — a key in the unit table (autocomplete); it becomes eng_unit. Temperature = C. Missing unit? Leave empty and add it to the table rather than inventing a spelling.
  • scale — a key in the scaling table. Doc says "value × 0.1" → x0.1. The table supplies the whole block at once: scale factor plus raw and engineering min/max.
  • dec — 0–3 display decimals, written as format = %.Nf. Blank leaves the format empty. Pair it with the scale: x0.1 → dec 1.

Behaviour — alarm, rw, freq, onl

  • alarm — priority letter written to plant_pri: A alarm (the fleet default), B/C lower priorities, N note. With auto_groups and alarms_to_alm both on, a lettered row is moved into the alm group.
  • rw — rw only when the documentation says the register is writable (setpoints, commands); everything else r. Bit rows are promoted to vr/vrw automatically. Writable rows also get the write half of the driver id.
  • freq — polling override; blank means derived, which is almost always right: analog and integral values poll norm read-only / slow writable, digital IO polls slow. Override with fast, norm, slow, once or never — use slow for rarely-changing measured values such as energy totals. Logging follows from it: norm/fast log min/1; on slow, read-only analog and integral values still log min/1 (house rule 2026-08-18) while setpoints and digitals log on change; once/never log on change.
  • onl — tick on 3–4 reliable, always-readable points (a temperature or status register). IWMAC uses them to detect that the unit is online, and validation fails when no point is marked.

Display extras — state, no grp

  • state — id of a list from the State texts card; it is serialized to IWMAC JSON in format_extra, so the operator sees Drift rather than 1. Suppressed for read-only rows when statetext_only_rw is on.
  • no grp — keep this row out of the groups block, so it exists as a parameter but does not appear in the operator's menu. Synthesized motherwords are excluded on their own while exclude_motherwords_from_groups is on.

Finding your way around a long list

  • Search filters on every column at once - group, text, datatype, address, unit. Ctrl+F or / anywhere on the page jumps into it, Esc clears it. The chip beside it reads 12 of 200 shown whenever anything is hidden.
  • It does not need to be exact. Several words all have to match, in any order and in any column, so tilluft temp finds Temperaturgiver tilluft. æ ø å can be typed ae o a - kjoling finds Kjøling. And if nothing matches exactly you get near misses instead, a letter or two out, with the chip marked ≈ 3 of 200 shown so you can see the answer is approximate. Exact matches are never diluted: the relaxed pass only runs when the strict one found nothing.
  • Numbers are never approximated. An address is an identity, not a description, so 101 will not offer you 1010. A term containing a digit always has to match exactly.
  • ++ starts the next word, so RT601++temp is the same search as RT601 temp — both terms have to match. Useful when you are typing a tag and then the thing you want off it without stopping for the space bar. You type the word; nothing is filled in for you.
  • Use it instead of the browser's find. The table keeps about fifty rows on screen however long the list is, so Ctrl+F is taken over deliberately: the browser's own find can only see the rows currently rendered, and on a long list it will report nothing for a tag that is there, or stop at the first of several matches. This box filters the whole list. Shift+Ctrl+F still opens the browser's own, for searching the page's text rather than the points.
  • The counting chips filter. Click bits, writable, alarms or online to show only those rows; click again to release. They combine, so writable + alarms is both.
  • ⛶ maximises the card to the whole window for editing a long list, with the header row still pinned. Esc closes it.
  • Click a column header to sort - ascending, descending, then back to project order. Sorting only changes what you are looking at. The project keeps its own order, because the sequence the points are written in decides each group's view_order, and that is the order the operator's menu appears in. The row numbers stay with their rows, so out-of-sequence numbers are the sign that you are in a sorted view.
  • To make a sort real, press keep this order, which appears while a sort is active. That rewrites the project order and therefore the generated view_order values.
  • Hiding a row does not exclude it: filters and search are display only. Everything still validates and generates.

Editing many rows at once

  • Click anywhere on a row to highlight it, and keep the button down while dragging up or down to take in the rows you pass. Shift-click extends from the last one, Ctrl-click adds or removes a single row, Esc clears. Clicking a cell still puts the cursor in it, so a single click both marks the row and lets you type.
  • The bar appears once two or more rows are highlighted - one row on its own is just the row you are working in.
  • A bar appears under the table: pick a column, give a value, and apply writes it to every selected row. fill down instead copies that column's value from the topmost selected row into the rest, leaving every other column alone.
  • duplicate copies each selected row with addr + 1; delete removes them all.
  • addr and bit are deliberately missing from the column list — writing one address across many rows would produce duplicate driver_ids and fail validation. Use ⧉ or duplicate, which step the address for you.
  • Selection follows what is on screen: rows hidden by search or a filter drop out of it, so a bulk edit can never change a row you cannot see.

Undo

  • ↶ undo, or Ctrl+Z, steps back through the last 10 changes to this table - cell edits, adding and deleting rows, duplicating, the bulk edits and keep this order. The button's tooltip names the change it will reverse.
  • Typing counts as one step per field, not per keystroke: the state is taken when you enter a cell and kept only if you actually changed something.
  • Undo restores rows whole, including the fields this table does not show (element_id, menu, active, the ranges). Loading or starting a project clears the history.

Working with rows

  • ⧉ duplicates a row with addr + 1 — the fastest way through a sequential register block. Every driver_id and element_id must be unique; duplicates are caught by Validate.
  • A project file can carry fields this table does not show — element_id, menu, active, range_min/range_max. They are preserved on load and written back out untouched; editing a row here does not drop them.

Units & driver (iw_sys)

help
Registers the physical devices and the driver in IWMAC — the iw_sys_* blocks at the end of the SQL. An existing plant already has these: leave both boxes unticked and the card emits nothing. Tick one only when this script is the thing that registers them - a new device, or a complete-plant script.

The two blocks

  • add the devices — one iw_sys_plant_units row per device in the list below, plus the order-number link.
  • add the driver — the iw_mb.exe process registration and every driver communication setting.

A band whose checkbox is off is dimmed and disabled — tick the box that writes it before filling it in. Values already in a loaded project are kept either way; they are simply not editable until the box is ticked. Communication opens with add the devices — you configure how to reach a bus while listing what is on it — but it is written under add the driver. The line beside the boxes names either mismatch.

Driver identity

owner / driver name ties the whole card together — it is the settings owner, the driver_type and the process name in one (EM270, GRUNDFOS), and both blocks use it. reg.type and order no stay blank unless the delivery specifies them. addr prefix: 0_ for the first driver on the plant, 1_ for the second — it is put in front of every device address for you.

Devices

One row per physical unit on the bus — ID01 / Carel EVD 01 / addr 1, ID02 / Carel EVD 02 / addr 2 … The band label counts them, and ⧉ duplicates a device with the id and address stepped, so a string of identical controllers is one row and a run of clicks. view order sorts the device list in IWMAC.

Communication

The mode select shows only the fields it uses: tcp — IP of the device or gateway, port 502 unless documented otherwise; rtu — COM port on the IWMAC machine, baud, parity and stop bits, which must match every device on the bus. Values land in iw_sys_plant_settings; everything not shown here uses the standard driver defaults.

Result

help

The three buttons

  • Validate — every check, nothing generated. Run it freely while editing.
  • Generate SQL — validates, then shows the script here. Nothing is written anywhere.
  • Generate + save file — the same, and writes the …SQL File.txt (browser build: downloads it). Import that file into the plant database as before.

Then, on the IWMAC side

  • The script is not the end of the job. In the IWMAC tooling: Setup Statetext → JSON Setup → Generate Param/Grp/Set, which must report Done, then Generate SQL. Same sequence for a first import and for a later update.
  • If that step reports errors, fix them there before continuing. Carrying on and hoping is how a half-imported list happens.

Reading the outcome

  • A green dot with Valid and the point/group counts means clear to generate. The same verdict sits beside the Validate button in the toolbar, and dims when you edit afterwards.
  • Errors list in red, block generation, and mark the failing rows red in the Points table — a failing chip up there shows only those rows.
  • Amber warnings (missing motherwords, blank alias texts) do not block, but deserve a look before delivery.

How to fix

On failure, a blue panel follows the errors: one recommendation per error kind, naming the points it applies to. Where a safe mechanical repair exists it carries a fix: button that applies the repair and validates again — point edits are undoable, option changes show as amber deviations. Judgement calls (duplicate ids, unknown table keys, which points get online) stay manual.

The script

The chip counts the rows it writes — the same figure in either SQL format. copy SQL puts the whole script on the clipboard; export SQL downloads exactly these bytes, cp1252-encoded the way the IWMAC tables expect — Norwegian text survives.

Workflow & tips

the workflow — the cards in page order
  1. Project — table name + plant; check subtract_one against the device docs. Amber options differ from the recommended defaults.
  2. Groups — start with the defaults, rename to the plant's zones.
  3. State texts — one list per enumeration; paste a vendor list straight in.
  4. Points — type them, or Import project a Copilot-authored JSON.
  5. Units & driver — only for a new/complete plant; both blocks off when the plant already has its driver.
  6. Validate — fix what the advice panel lists; failing rows are marked red.
  7. Generate — review, then copy SQL or export SQL.
keyboard
  • Ctrl+F or / search the points · ++ in the search starts the next word · Ctrl+Z undo (10 steps) · Esc clears search, then selection, then fullscreen
  • Click a row and drag to select many; Shift-click extends, Ctrl-click toggles one
  • Enter in a state-text word box adds the next state
tips
  • Before the list exists, prove the device answers. A list built against a register map the device does not implement is legal, complete and wrong, and you find out on site. ping, then modpoll on one register you already know the right answer to. The unit ID and the serial settings are what to suspect first when nothing comes back.
  • Start a project: New for an empty one, pick a saved one from the list, or bring one in — Import project for a .json/.yaml, Import SQL for a generated script, Insert Excel for a filled Modbustemplate workbook.
  • Then work down the page: Project for the table name, plant number and options · Groups and State texts for what the operator sees · Points for the register list · Units & driver only when this plant's devices are not registered yet.
  • Editing points: Ctrl+F finds rows, click and drag selects several, and the bar under the table changes them together. ⤓ points saves the list as its own file, ⤒ points appends one from somewhere else.
  • Finish with Validate, then Generate SQL. Validate lists what would stop the import; warnings do not block. A project built from an imported SQL script has no plant number in it — set one before generating.
  • Save keeps a copy in this browser. Export writes the real file — that is the one to keep, mail, or move to another machine. It names itself from the project: 10225_spar_hansnes_vent_25.08.2026_14.32.json — plant, table, date and 24-hour time. Two exports in the same minute get the same name, so the browser numbers the second one. Put a .yaml in the name box for YAML instead of JSON.
  • Direct link: add #file-name to the URL, e.g. …/#example-belimo-ev.json.

New Modbus variable

Clone the nearest existing datatype and change what differs. Every field but the name is a value the shipped table already uses, so the row stays a combination of parts the driver understands.
